# OSHIRU 開発・公開ロードマップ

## 基本方針
OSHIRUは「推し活グッズを探す・比較する・保存する」ための検索補助サービスとして設計する。検索結果の正確性、権利処理、速度、視認性を優先し、取得できない情報を推測で埋めない。

本番 `main` は一般公開停止状態を維持し、開発は `develop-v2` で行う。公開判定を通過するまでProductionへ戻さない。

## 第1ステップ — 公開可能な検索体験を作る

### P0 UI整理
- [x] 接続状況を利用者向けUIから削除
- [x] 「通販API」の内部実装名を利用者向けUIから削除
- [x] 未実装の通知導線を削減し「保存した検索」に整理
- [x] v5の基本構成を維持し、商品カードの文字・価格を拡大
- [x] 3列中心の結果表示に変更して視認性を確保
- [x] 軽量なOSHIRUカットインをCSSだけで実装
- [x] 比較表を「料金 / 状態 / 更新時期」で切替可能にする
- [ ] 実機で iPhone / Android / PC の表示確認
- [ ] キーボード操作・スクリーンリーダー確認

### P0 データ取得・API
優先順位:
1. Yahoo!ショッピング商品検索API（公式・商品データ）
2. 楽天市場商品検索API（公式・商品データ）
3. AniList（作品・キャラクター候補補助）
4. メルカリ / Yahoo!フリマ / Yahoo!オークションは、許可された取得方法がない限り個別検索リンク・確認済み情報を中心にする
5. X APIは従量課金のためMVPでは後回し

APIキーはブラウザに埋め込まず、Vercel Environment Variablesでサーバー側だけに保存する。

### P0 著作権・画像ポリシー
- 販売者や第三者が撮影した画像を無断でOSHIRUへコピー保存しない
- 公式APIが画像URLを返し、利用条件上表示できる場合だけ表示する
- 権利状態が不明な画像はプレースホルダー + 販売元リンクにする
- OSHIRUが公式サービスだと誤認されるロゴ・ドメイン・表現を避ける
- キャラクター名・作品名は検索語/商品識別のため必要最小限に使用する
- 公開・収益化前に必要に応じて専門家レビューを入れる

### P1 画像検索POC
「Web全体から完全一致画像を逆検索する」のではなく、まず以下を実装する。

1. ユーザーが画像/スクリーンショットを選択
2. サーバー側Visionで、画像内の文字・作品候補・キャラ候補・グッズ種別を抽出
3. 信頼度と複数候補を返す
4. ユーザーが候補を選ぶ
5. その検索語をYahoo!/楽天/確認済み出品へ渡す

成功基準:
- 20枚以上のテスト画像で検索語候補を評価
- キャラ/作品/グッズ種別のいずれかを正しく抽出できる率 80%以上を最初の目標にする
- 誤判定時にユーザーが修正できる
- AI判定を「確定」と表示しない

## 第2ステップ — 公開βと計測

### SEO
公開前:
- 開発版は `noindex`
- 公開版だけ `index,follow`
- sitemap.xmlをルートに設置
- Search Console所有権確認
- 商品の0件ページ・エラー・ユーザー固有ページは原則noindex
- 将来的な作品/キャラ/コラボ別ページは固定URLを持たせる
- title / description / canonical / OGP をページ単位で設定
- Core Web Vitalsを確認

SEOで増やすページ候補:
- `/works/{slug}` 作品別グッズ検索
- `/oshi/{slug}` キャラ/メンバー別
- `/collab/{slug}` コラボ別
- `/guide/...` 推し活グッズの比較・探し方

検索結果を無制限にインデックスさせるのではなく、「ユーザーに独自価値がある固定ページ」をSEO対象にする。

### 無料計測
公開初期は次を確認する。
- 週次利用者数
- 検索回数
- 検索0件率
- 販売元へのクリック率
- お気に入り率
- 保存検索率
- 再訪率
- デバイス別離脱
- Core Web Vitals

無料開始案:
1. Search Console: 検索表示回数 / CTR / クエリ / インデックス
2. Vercel Web Analytics: ページビュー等の軽量確認
3. GA4: 検索・商品クリック・お気に入り等の詳細イベントが必要になった段階で導入

### 個人データ
Phase A: ログインなし
- お気に入り/保存検索はlocalStorage
- サーバーに個人別履歴を送らない

Phase B: アカウント
- DBに user_id / favorites / saved_searches を保存
- メール・認証は認証基盤へ委譲
- 利用目的・保存期間・削除方法をプライバシーポリシーに記載

Phase C: トレンド分析
- 個人単位ではなく集計データを優先
- 例: コラボ別検索回数、商品種別別クリック率、価格帯別CTR
- 少人数セグメントの公開や個人推定をしない

広告・行動ターゲティングを開始する場合はCookie/識別子の利用目的、第三者提供、同意設計を再レビューする。

## 無料サーバー → 有料へ移る判断

### 独自ドメイン
独自ドメインは「利用者が増えてから」ではなく、一般公開βの前後で取得する方がよい。
理由:
- ブランドを固定できる
- 後からドメイン変更するSEO移行作業を減らせる
- 公式性/信頼性の説明がしやすい
- メールアドレスを `contact@...` に統一できる

### Vercel Hobbyを維持できる期間
- 非商用の検証・個人プロジェクト段階
- 利用量が無料枠内
- 高頻度のバックグラウンド収集が不要

### Proへ移るトリガー
次のどれか1つで移行検討を開始する。
- アフィリエイト/広告など商用利用を開始する
- 過去30日で無料枠の70%を継続して超える
- 監視/クロール/更新ジョブを日次以上の頻度で安定運用する必要が出る
- ログ保持・カスタム分析・チーム運用が必要になる
- APIレスポンス遅延/実行時間制限がサービス品質を妨げ始める

「ユーザー数だけ」で移行を決めない。Vercel UsageでCPU、Function Invocations、転送量、Analytics Eventsを30日単位で見る。

## サービスとしての成長判定
公開βで4〜8週間を1サイクルとして確認する。

継続投資の目安（OSHIRU内部の事業KPIとして使用する仮基準）:
- WAU 300以上: ニーズの初期確認
- WAU 1,000以上: 独自コンテンツ/通知/アカウントへの投資を強化
- 4週間再訪率 20%以上: 習慣利用の兆候
- 販売元クリック率 10%以上: 比較結果が購買行動に繋がっている兆候
- 0件率 20%以下を目標にデータ取得範囲を改善

これらは外部統計ではなく、OSHIRUの運営判断用の仮説値。実データを見て更新する。

## 第3ステップ — 複数サービス化
OSHIRU固有コードと共通基盤を分離する。

共通化するもの:
- 検索UI
- Source Adapterインターフェース
- 正規化データモデル
- 比較表
- お気に入り/保存検索
- SEOテンプレート
- Analyticsイベント
- 法務ページテンプレート
- 通知基盤
- APIキャッシュ/レート制限

固有化するもの:
- 商品カテゴリ
- 検索辞書/エイリアス
- データ取得元
- ブランド/コピー
- 比較項目

大量生産より先に「1サービスで再現性のある獲得・継続・収益」を確認してから横展開する。
